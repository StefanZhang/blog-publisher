# Independent likes Worker publication

`deploy-likes.yml` is a manual, independent publication path for the existing `sfz-likes` Worker. It does not publish Pages, change DNS/routes/cron, execute D1 schema, create a database, or set/rotate SALT. The separate `CLOUDFLARE_LIKES_API_TOKEN` belongs only to the existing protected `preview` Environment and needs Worker script editing for this account; do not grant D1 or DNS/route writes and do not reuse or expand the Pages token.

The workflow checks out trusted publisher `main` and requires its current successful controller check, protected main and the exact human reviewer enforced by `controller.mjs stage`. The entry point additionally requires the exact `deploy-likes.yml@refs/heads/main` workflow identity, `workflow_dispatch`, exact Node 24.22.2 and the expected job. `inspect` has no Cloudflare secret. Its content-free source run/commit, artifact hash, ID hash/count are the review subject. The `publish` job waits for the existing preview human approval and repeats current-main/sealed-source verification with those exact identities.

Source bytes come from the private repository's completed current-main build and its `sealed-<run>-<attempt>` privateRelease archive, checked by the existing trusted controller. Only `record.contentIds` data are used to generate `known-ids.js`. The private repository's `workers/likes/src/index.js` and `schema.sql` are downloaded at that exact commit and individually checked against `likes-policy.json`; schema is never executed. No private build script, package manifest, Wrangler config or generated ID JavaScript is executed or trusted. Wrangler compiles only the approved Worker module and publisher-generated ID module.

The maintainer allocated the empty `sfz-likes` D1 as `9813abef-6420-47c3-977a-4fab4c97e53d`; this allocation does not prove schema or Worker readiness. Null/placeholder database IDs are rejected. The maintainer must apply the approved schema once, configure the fixed DB binding and stable SALT (at least 32 characters), verify the independent rehearsal, and establish the custom domain/cron. Existing `uptimeflare_d1` is unrelated. This ordinary workflow cannot perform bootstrap and refuses an absent Worker, secret or ID metadata.

For the separate, reviewed maintainer bootstrap, `stageLikesPackage({env, sourcePolicy, api, root, policy})` is the shared staging API. It runs the same controller stage/current-main CI/privateRelease/seal checks and returns `{record, run, worker, ids, schemaBytes}`. `api(endpoint)` is the caller's authenticated, read-only private-repository JSON API; `root` must be the checkout's fresh `.work` directory because the trusted controller stage uses that location. `worker` contains only the SHA-approved module, generated ID module and generated Wrangler config. `schemaBytes` contains the SHA-approved SQL buffer for a separately authorized one-time bootstrap; this API never executes it. The maintainer entry point must enforce its own exact approved GitHub workflow/commit and bootstrap authorization before calling the API, and must not log returned source buffers or upload `.work`.

Bootstrap must also set these plain-text bindings on the active Worker version:

- `ALLOWED_ORIGIN`: exactly the three origins in policy, joined with commas.
- `KNOWN_IDS_JSON`: JSON encoding of the unique, lexicographically sorted string ID array.
- `KNOWN_IDS_SHA256`: SHA256 of those exact UTF-8 JSON bytes, without a trailing newline.

Only numeric post IDs and `note-NN` metadata are public; no article/comment contents or private archives enter this repository or receipt. The policy baseline IDs come from the reviewed initial set. The active deployment must be one version at 100%; its exact five bindings must prove SALT exists as `secret_text`, DB matches the pinned UUID, and the ID metadata/hash agree. Unknown bindings are rejected rather than accidentally removed by a code update. Every next set must contain both the policy baseline and **all currently deployed IDs**, including additions made by previous releases. Missing metadata is a bootstrap blocker, not permission to reset the set. Read-only `/health`, likes and views checks also prove existing schema/SALT readiness, every prior ID and CORS before any upload.

The exact commands are `npx --yes wrangler@4.45.0 versions upload --experimental-auto-create=false ...` and, after checking the uploaded version's bindings and rechecking source main/active deployment, `versions deploy <version>@100% --yes`. The generated config has no routes, triggers, build commands, asset directories or secret values. This avoids the ordinary `wrangler deploy` trigger reconciliation path. Pinned [Wrangler 4.45.0 source](https://github.com/cloudflare/workers-sdk/blob/wrangler%404.45.0/packages/wrangler/src/versions/upload.ts#L698-L710) inherits secrets with `keepSecrets: true`; its [upload guidance](https://github.com/cloudflare/workers-sdk/blob/wrangler%404.45.0/packages/wrangler/src/versions/upload.ts#L915-L923) explicitly requires the separate `triggers deploy` command for routes, custom domains and cron changes. We never invoke that command. SALT values are not readable through binding evidence; the maintainer must not rotate them outside this process.

On success, `.work/likes-receipt.json` records the source/controller identities, sealed artifact hash, previous/new Worker version, deployment ID and ID hash/count. Only this file is uploaded as the workflow artifact. Wrangler output is captured and never echoed, avoiding accidental provider/secret disclosure. HTTP acceptance uses GET only; it neither creates likes nor counts views. A failed upload leaves traffic unchanged. A failed promotion/postcheck attempts a guarded version rollback only when the active version is still this run's uploaded version: it revalidates both versions' ID metadata and rechecks the active deployment ID immediately before restoring the previous version to 100%. It then confirms that version and its IDs, repeats read-only HTTP acceptance, and checks the deployment did not change during acceptance. A detected concurrent maintainer deployment stops rollback without overwrite. Unreadable state, rollback command failure, identity mismatch or failed recovery acceptance produces a distinct inspection-required failure, not a success receipt. The workflow never reruns schema or rotates SALT. An interruption after promotion but before receipt may leave the new version active; the next run derives its monotonic ID baseline from that active version, not from a missing receipt.

Tests: select Node 24.22.2, run `npm test`, `python3 -m unittest discover -s tests -p 'test_*.py'`, and pinned `actionlint`. Tests inject source/API/Wrangler boundaries and perform no remote writes. They do not replace the first isolated D1/Worker rehearsal or real post-deployment HTTP acceptance. GitHub concurrency serializes this workflow, and the active version is checked immediately before promotion; Cloudflare's deployment API provides no compare-and-swap here, so maintainers must not publish concurrently outside the workflow.
